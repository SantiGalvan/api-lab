# Scenario seed-and-verify, generic scenario runner, and packaging

## Context
Ticket 4 of the api-lab build-out, blocked by Ticket 2's m2m Task CRUD (not by Ticket 3 — this scenario stays in `m2m` auth mode, it never calls `login()`). The goal: a demonstrable scenario that mixes sequential and concurrent steps on real Tasks, a generic runner to launch any scenario, and the supporting files (README, `.gitignore`, npm script) that let another developer use the tool without verbal explanation.

While building the scenario, `MyTask.postman_collection.json` (added to the repo for reference) showed that MyTask's real `POST/PUT /tasks` expects the Task fields nested under a `task` key, and includes fields beyond the placeholder `title` used by Ticket 2/3's tests (`name`, `project_id`, `user_id`, `task_type_id`, ...). Making the scenario actually work against the real API required revisiting `apps/mytask/api.js`'s request shape — confirmed with the user before implementing, since it changes a contract from an earlier ticket.

## Technical changes
```js
// apps/mytask/scenarios/seedAndVerifyTask.js — seed step: 20 concurrent
// creates capped at 8 in flight, using the same mapLimitSettled the rest of
// the scenario reuses for read-back and cleanup.
const seedResults = await mapLimitSettled(
  Array.from({ length: SEED_COUNT }, (_, index) => index),
  (index) => api.createTask(buildSeedPayload(env, index)).then(unwrapTask),
  { concurrency: CONCURRENCY },
);
```

```js
// apps/mytask/api.js — MyTask's real Task Create/Update body nests the
// fields under a "task" key (Rails-style params wrapping); api.js used to
// send the bare payload, which the real API rejects.
function createTask(payload) {
  return strategy.request((token) => post(buildUrl(env.baseUrl, 'tasks'), { task: payload }, { token }));
}
```

## Rationale
`unwrapTask()` normalizes a `{ task: {...} }`-or-bare response into the bare shape before the scenario reads `.id`/`.name` off it: the Postman collection only confirms the *request* envelope, not whether Show/Create responses echo the same wrapping, so the scenario stays correct either way instead of assuming one shape and breaking against the real server. `user_id`/`task_type_id` are included in the seed payload only when their fixture env vars are set, rather than being required like `project_id` — the ticket only mandates a fixture Project, so a setup without the other two fixtures still runs (creates may then fail validation on the real server, which the report faithfully counts as `failed` rather than the scenario refusing to run). `scenario.js` resolves `apps/<app>/scenarios/<name>.js` before falling back to the root `scenarios/<name>.js`, mirroring `CONTEXT.md`'s Scenario/Cross-app scenario distinction without the runner needing to know which kind it was handed. The scenario itself owns saving its report (via `core/report`) rather than the runner, since a future scenario could reasonably want a different name or extra fields in its report — the runner only resolves and executes.

Verified end-to-end with a throwaway local HTTP stub standing in for MyTask (no real MyTask credentials/network available in this environment): `npm run seed` produced a real `runs/*.json` report with 20/20 ok on seed, read-back, and cleanup, and a passing stateful update check.
