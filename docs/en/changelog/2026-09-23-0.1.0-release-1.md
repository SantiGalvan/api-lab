## Technical changes
```js
// core/client/client.js — 401 is deliberately excluded from the generic error path:
// client.js has no notion of "auth", so it hands the raw 401 back to the caller
// (core/auth.js) to decide whether a refresh makes sense.
if (!response.ok && response.status !== 401) {
  throw new HTTPError(response.status, body);
}
```

```js
// core/auth/auth.js — the login strategy is the only place that knows a 401
// means "stale token": it retries the same requestFn exactly once with a
// freshly-logged-in token, then gives up.
if (result.status !== 401) {
  return result.body;
}
cachedValue = await login();
const retryResult = await requestFn(toToken(cachedValue));
if (retryResult.status === 401) {
  throw new HTTPError(retryResult.status, retryResult.body);
}
return retryResult.body;
```

## Rationale
`client.js` stays deliberately ignorant of "M2M" or "login" as concepts (per ADR 0001): it only knows two token transports (query string, header) and treats 401 as data, not as an automatic failure, because only the auth layer can tell whether a 401 is retryable. `auth.js` exposes both strategies behind the same `request(requestFn)` shape so callers don't need to branch on which auth mode is active — the shape is identical whether the token never changes (`m2m`) or is refreshed lazily (`login`). `concurrency.js` is a thin wrapper over `p-limit` rather than a hand-rolled scheduler, since `p-limit` already covers fail-fast (`Promise.all`) and settled (`Promise.allSettled`) semantics correctly. `report.js` takes an injectable `dir` so tests never touch the real `runs/` folder, defaulting to `runs/` for real usage.
