# Scenario seed-and-verify, runner generico per scenari, e packaging

## Contesto
Ticket 4 del build-out di api-lab, bloccato dal CRUD Task in modalità m2m del Ticket 2 (non dal Ticket 3 — questo scenario resta in modalità di autenticazione `m2m`, non chiama mai `login()`). L'obiettivo: uno scenario dimostrabile che mescola step sequenziali e concorrenti su Task reali, un runner generico per lanciare qualunque scenario, e i file di corredo (README, `.gitignore`, script npm) che rendono lo strumento usabile da un altro sviluppatore senza spiegazioni verbali.

Durante la costruzione dello scenario, `MyTask.postman_collection.json` (aggiunto al repository come riferimento) ha mostrato che le vere `POST/PUT /tasks` di MyTask si aspettano i campi del Task annidati sotto una chiave `task`, e includono campi oltre al `title` fittizio usato dai test dei Ticket 2/3 (`name`, `project_id`, `user_id`, `task_type_id`, ...). Per far funzionare davvero lo scenario contro l'API reale è stato necessario rivedere la forma delle richieste in `apps/mytask/api.js` — confermato con l'utente prima di implementare, trattandosi di una modifica a un contratto stabilito in un ticket precedente.

## Modifiche tecniche
```js
// apps/mytask/scenarios/seedAndVerifyTask.js — step di seed: 20 create
// concorrenti con tetto di 8 in volo, riusando lo stesso mapLimitSettled
// che il resto dello scenario riusa per rilettura e cleanup.
const seedResults = await mapLimitSettled(
  Array.from({ length: SEED_COUNT }, (_, index) => index),
  (index) => api.createTask(buildSeedPayload(env, index)).then(unwrapTask),
  { concurrency: CONCURRENCY },
);
```

```js
// apps/mytask/api.js — il vero body di Task Create/Update di MyTask annida
// i campi sotto una chiave "task" (params wrapping in stile Rails);
// api.js inviava il payload nudo, che l'API reale rifiuta.
function createTask(payload) {
  return strategy.request((token) => post(buildUrl(env.baseUrl, 'tasks'), { task: payload }, { token }));
}
```

## Motivazione
`unwrapTask()` normalizza una risposta `{ task: {...} }`-oppure-nuda nella forma nuda prima che lo scenario legga `.id`/`.name`: la collection Postman conferma solo l'envelope della *richiesta*, non se le risposte di Show/Create rispecchiano lo stesso wrapping, quindi lo scenario resta corretto in entrambi i casi invece di assumere una forma e rompersi contro il server reale. `user_id`/`task_type_id` sono inclusi nel payload di seed solo se le rispettive variabili env di fixture sono impostate, a differenza di `project_id` che resta obbligatorio — il ticket richiede solo un Project di fixture, quindi un setup senza le altre due fixture funziona comunque (le create potrebbero fallire la validazione sul server reale, e il report lo conta fedelmente come `failed` invece di rifiutarsi di girare). `scenario.js` risolve prima `apps/<app>/scenarios/<nome>.js` e ricade poi su `scenarios/<nome>.js` alla radice, rispecchiando la distinzione Scenario/Scenario cross-app di `CONTEXT.md` senza che il runner debba sapere di che tipo si tratti. Lo scenario stesso possiede la responsabilità di salvare il proprio report (via `core/report`) invece del runner, perché un futuro scenario potrebbe ragionevolmente volere un nome diverso o campi extra nel proprio report — il runner si limita a risolvere ed eseguire.

Verificato end-to-end con uno stub HTTP locale usa-e-getta al posto di MyTask (nessuna credenziale/rete reale verso MyTask disponibile in questo ambiente): `npm run seed` ha prodotto un report reale sotto `runs/*.json` con 20/20 ok su seed, rilettura e cleanup, e un controllo di update stateful superato.
