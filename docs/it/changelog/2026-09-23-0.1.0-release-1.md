## Modifiche tecniche
```js
// core/client/client.js — il 401 è deliberatamente escluso dal percorso di errore generico:
// client.js non ha alcuna nozione di "auth", quindi restituisce il 401 grezzo
// al chiamante (core/auth.js), che decide se un refresh ha senso.
if (!response.ok && response.status !== 401) {
  throw new HTTPError(response.status, body);
}
```

```js
// core/auth/auth.js — la strategia login è l'unico punto che sa che un 401
// significa "token scaduto": ripete la stessa requestFn esattamente una volta
// con un token appena rinnovato, poi si arrende.
if (result.status !== 401) {
  return result.body;
}
cachedValue = await login();
const retryResult = await requestFn(toToken(cachedValue));
if (retryResult.status === 401) {
  throw new HTTPError(retryResult.status, retryResult.body);
}
return retryResult.body;
```

## Motivazione
`client.js` resta deliberatamente ignaro dei concetti "M2M" o "login" (come da ADR 0001): conosce solo due modalità di trasporto del token (query string, header) e tratta il 401 come dato, non come un fallimento automatico, perché solo lo strato di auth può sapere se un 401 sia ritentabile. `auth.js` espone entrambe le strategie dietro la stessa forma `request(requestFn)`, così i chiamanti non devono ramificare in base alla modalità di auth attiva — la forma è identica sia che il token non cambi mai (`m2m`) sia che venga rinnovato lazy (`login`). `concurrency.js` è un sottile wrapper su `p-limit` invece di uno scheduler scritto a mano, dato che `p-limit` copre già correttamente la semantica fail-fast (`Promise.all`) e settled (`Promise.allSettled`). `report.js` accetta una `dir` iniettabile così i test non toccano mai la vera cartella `runs/`, con default a `runs/` per l'uso reale.
