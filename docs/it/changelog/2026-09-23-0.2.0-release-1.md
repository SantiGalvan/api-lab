# App mytask: config + Task CRUD in modalità m2m + REPL

## Contesto
Ticket 2 della costruzione di api-lab, bloccato dal motore condiviso del Ticket 1. La prima app reale: uno sviluppatore può aprire una REPL su `mytask` e fare CRUD reale sulla risorsa Task come oggetti JS puri, autenticandosi con un token m2m pre-provisionato (come da ADR 0001).

## Modifiche tecniche
```js
// apps/mytask/api.js — ogni funzione di dominio è una composizione sottile
// del verbo HTTP del motore condiviso + la strategia di auth dell'app; nessuna
// chiamata fetch avviene al di fuori di core/client.
function getTask(id) {
  return strategy.request((token) => get(buildUrl(env.baseUrl, `tasks/${id}`), { token }));
}
```

```js
// repl.js — generico rispetto alle app future: non fa mai riferimento a "mytask"
// esplicitamente, assume solo che config.js/api.js di ogni app esportino come
// default rispettivamente getEnvironment/makeApi.
const { default: getEnvironment } = await import(`./apps/${appName}/config.js`);
const { default: makeApi } = await import(`./apps/${appName}/api.js`);
```

## Motivazione
`config.js` espone i campi dell'ambiente come getter su `process.env` invece che come oggetto letterale, così i test possono stubbare le variabili d'ambiente caso per caso senza scontrarsi con la cache dei moduli ESM. `options.authMode` di `makeMytaskApi` di default vale `'m2m'` e lancia un errore per qualsiasi altro valore — la modalità `login` esiste come concetto nell'ADR 0001 ma questa app non ha ancora credenziali di login configurate, quindi fallire in modo esplicito è preferibile a un comportamento scorretto silenzioso. `repl.js` risolve la coppia app/ambiente tramite una convenzione di export `default` su `config.js`/`api.js` invece di avere `mytask` scritto a mano, così la prossima app ottiene una REPL gratis seguendo la stessa forma.
